本文回答一件事：群模板配好、点了开始群聊之后，**熔炉怎么知道你此刻在干什么**（例如「做一份工作总结」）。这不是再堆一套工具，是 **prompt 工程：角色壳 × 情境包**。

原计划里的「3.2 Grok 客户端」后置，见 [crucible-3x-plan.md](./crucible-3x-plan.md)。

---

## 1. 问题

3.1 已经把熔炉拆成互不串的角色：成员适配、节点适配、系统审核。那三份 prompt 只回答 **「这一轮你是谁、不许干什么」**。

用户开一场群聊时真正要的是另一句话：

> 这不是抽象的 Agent。我正在跑「周报工作总结」这条流水线；开聊时我说了「把本周做的事收成一段给老板」。你要按这个理解后续审核、总结、插话。

如果只把角色 prompt 丢给 Grok：

- 它不知道群标题、步骤议程、当前停在哪一步。
- 它看不到开聊时你填的那句话（那句话往往就是意图）。
- 把整段聊天记录塞进 prompt 会胀、会串味、会把密钥和过期争执一起喂进去。

所以 3.2 的对象是 **情境（situation）**，不是第四套业务工具。

---

## 2. 设计思路（两根轴，不要揉成一团）

把熔炉要读的东西分成正交的两根轴：

| 轴 | 变不变 | 回答什么 | 文件 |
| --- | --- | --- | --- |
| **角色壳** | 慢。一次只装一套 | 你是适配还是审核还是主持；禁止越权 | `prompts/*.md` + `memory/*.md` |
| **情境包** | 快。随这场会话刷新 | 你正在做哪件事、议程、当前步、用户原话 | `data/furnace/SITUATION.md` |

本机 Grok 的工作目录仍是 `data/furnace`。**唯一入口还是 `ACTIVE.md`**：角色壳 + 情境包拼在同一份里，避免模型自己去「再找三份记忆拼起来」。

```
ACTIVE.md
├── 熔炉本轮：{群聊主持 | 成员适配 | 节点适配 | 系统审核}
├── ## 此刻在做什么     ← 情境包（槽位固定，内容随会话变）
├── ## Prompt           ← 当前角色壳
└── ## 本机记忆         ← 只该角色的长期偏好，不写这场任务的事实
```

旁路再落一份 `SITUATION.md`，方便人打开核对；模型以 `ACTIVE.md` 为准。

第四个角色 **群聊主持**（`session`）补的是：开聊之后、还没轮到适配/闸门时，熔炉也要能懂这场群。它仍然 **没有工具**，只读情境说话。

---

## 3. 为什么是槽位填充，不是「再让模型总结一遍」

Prompt 工程这里选 **固定骨架 + 填槽**，不在注入层再调一次 LLM 去「提炼意图」。

| 做法 | 为什么 |
| --- | --- |
| 意图槽 **抄用户原话** | 「做工作总结」四个字比任何改写都准；改写会丢主语、语气、对象（给老板 / 给自己） |
| 议程槽 **抄群模板步骤** | 模板就是用户配好的计划；熔炉不许在注入层改编排 |
| 现在槽 **抄当前节点** | 和工作台流程轨同一真相（SQL 节点状态） |
| 事实槽 **抄 `#` 参数** | 与脚本契约同一套数；人已经用 `#1` 说过的话不要换一种说法 |
| 指针槽 **只给路径** | 群报告全文可能很长；需要细节时去读 `ANNOUNCEMENT.md`，不要在 ACTIVE 里再贴一遍 |

注入层 **禁止**：

- 把全部气泡历史拼进 ACTIVE。
- 用另一段 prompt 把本场任务写进角色记忆（记忆是偏好，不是本周周报）。
- 把三套角色 prompt 拼进同一份。
- 把密钥、Token、Adapter 原文默认喂给模型。

脚本成员继续走原来的 A/B 契约（占位符 + `ACW_*`）。熔炉是读 Markdown 的 Agent，**不要让脚本和熔炉抢同一份「偷偷塞的 system prompt」**。

---

## 4. 情境包骨架（给模型看的合同）

槽位名称写死，便于模型建立习惯。缺的槽写「（无）」，不要删标题。

```markdown
## 此刻在做什么

意图：{开聊通过时的原文；否则群简介；否则群标题}
这场群：{群标题} · 会话 {会话标题}
简介：{群 description}
工作文件夹：{路径或（无）}
议程：
  1. …
  2. … ← 现在
现在：{步骤名} · {节点状态}
已知 # 参数：
  - #1 …
群报告：{相对 data 的 ANNOUNCEMENT.md 路径，或（尚未生成）}
```

截断规则（实现口径）：意图约 2k 字；单个参数约 800 字；整份情境约 8k 字。超了留「…(截断)」+ 指针，不静默丢整段。

### 例子：工作总结

用户群模板：

- 标题：周报工作总结
- 简介：根据本周节点产出写一段给老板
- 步骤：收集材料 → 熔炉整理 → 人确认

开聊确认框里输入：`把本周做的事收成一段，语气正式一点`

熔炉读到的意图槽就是这句原文，不是「用户可能想要一份报告」。主持角色的 prompt 再规定：先按意图写/问，不改编排，不到闸门不要做通过/拒绝。

## 5. 何时写入（刷新节拍）

本机同一时刻只有一个 Grok cwd → **后写覆盖前一场**。产品口径：熔炉跟着你当前打开并推进的这场群。

| 时机 | 角色壳 | 情境 |
| --- | --- | --- |
| 群模板开聊（含启动确认） | 群聊主持 | 有群名片、议程；意图可能还只有简介 |
| 点「通过」启动 | 仍主持（除非下一步立刻适配/审核） | **意图改为开聊输入原文**；`#1…` 进入事实槽 |
| 用户在群里继续说话 | **保持当前角色**（审核中不要打回主持） | 更新意图近况 / `#` 参数 |
| 适配步开跑 | 节点适配或成员适配 | 现在槽对准该步 |
| 闸门要熔炉确认 | 系统审核 | 现在槽对准闸门节点 |
| 点精灵（未决） | 后置：是否切主持 | 至少应能读到最新 `SITUATION.md` |

聊天里 **不把情境全文做成气泡**。系统最多说「熔炉本轮：xxx」，详细只在 `data/furnace`。

## 6. 角色 prompt 怎么配合情境（分层指令）

每一份角色 prompt 顶部 implicitly 依赖「先读此刻在做什么」。分工如下：

| 角色 | 读情境之后干什么 | 仍然不许 |
| --- | --- | --- |
| 群聊主持 | 用意图+议程理解「这场是工作总结还是发布还是修脚本」；可以问缺哪一段材料 | 改步骤、改源文件、替闸门点通过 |
| 成员适配 | 看「现在」是哪个成员，把它接到工作台 | 写成工作总结、做审核 |
| 节点适配 | 看「现在」是哪一步，优先改代码，不行保留标记 | 改编排、做审核 |
| 系统审核 | 看该节点产出是否满足意图和闸门政策 | 重写业务代码、把未完成步骤当完成 |

主持是 **默认壳**：开聊就要懂事。适配/审核是 **临时换壳**，换壳时情境包留下，只换 Prompt + 对应记忆。

本机记忆仍然三套（加主持一套）互不覆盖。记忆里只准写「我喜欢正式语气 / 不要用英文标题」这类偏好，不准把「本周周报正文」存进记忆——正文在群报告和 `#` 参数里。

## 7. 和已有工作台账本的关系

| 账本 | 给谁 | 熔炉怎么用 |
| --- | --- | --- |
| 群模板 `title/description/steps` | 人配流程 | 议程槽 |
| 开聊闸门输入 / `kickoff` | 人表达本场目的 | **意图槽第一来源** |
| `context.paramsList`（`#1`…） | 人 + 脚本 | 事实槽；脚本仍走占位符 |
| 节点 SQL 状态 | 引擎 | 现在槽 |
| `ANNOUNCEMENT.md` 群报告 | 人扫读 | 指针；不整篇复制 |
| 聊天气泡 | 人看过程 | 不作为 ACTIVE 的主上下文 |

判定有没有跑偏：

> 关掉熔炉，这场群还能不能当普通流程跑。能。熔炉只是多读了一份它能懂的 Markdown。

---

## 8. 不做 / 后置

- 不为「让熔炉更懂」去新开 `step_type` 或新气泡种类。
- 不在注入层再调模型做摘要。
- 不把多场会话的情境拼进同一份 ACTIVE（cwd 只有一份）。
- 不把情境写入 git。
- 精灵点开切角色、Grok 客户端形态：后置。
- 自动把总结写进用户业务仓库：后置；本场总结应出现在节点输出 / 群报告，而不是偷偷改模板。

---

## 9. 验收

- 配一个标题或简介含「工作总结」的群，开聊后 `data/furnace/SITUATION.md` / `ACTIVE.md` 能看到这场群的标题、简介、步骤。
- 启动确认框里写「收成一段给老板」，通过后意图槽是这句原文。
- 进入适配步时 ACTIVE 角色变成节点/成员适配，情境仍在；进入熔炉闸门时变成系统审核，情境仍在。
- 主持 prompt 与审核 prompt 仍不拼进同一角色段。
- `npm test` 含情境拼接与截断。
