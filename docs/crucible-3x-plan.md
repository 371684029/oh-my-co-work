---

## 1. 实施原则

1. 先让熔炉出现在 **加人 / 加节点 / 建群 / 闸门** 上，再接 Grok 提示词跑通两条适配路径，再做桌面壳。  
2. 熔炉是 **Grok Agent，无内置工具**；产出必须是普通成员、普通适配节点、普通闸门记录。  
3. JSONL Adapter 只扩展文档与示例，不在 3.x 改成「熔炉私有协议」。  
4. 写代码、跑构建仍走 PTY（及可选 Adapter）；不新增脱离 `processRegistry` 的执行通道。  
5. 默认闸门执行者仍是人；熔炉是可选项。  
6. 模型提供方可替换，Grok / Grok Build 不写进引擎内核硬编码。  
7. 熔炉桌面与工作台共用本机 server；切换外壳，不切换数据面。桌面产品名就是「熔炉」。

---

## 2. 版本切分

| 版本 | 主题 | 交付边界 |
|------|------|----------|
| `3.0` | 熔炉能被配上 | 工作台出现熔炉（Grok Agent 入口）；加成员 / 加节点 / 建群可选；闸门执行者可配人 \| 熔炉；Grok 未接上时入口可占位 |
| `3.1` | 两条适配路径 | **加人：提示词驱动改代码适配**；**加节点：插入适配节点**。人（或熔炉闸门）确认后写入普通表结构 |
| `3.2` | Grok 编码/构建 | 对接 Grok Build；改仓库/构建仍走 PTY；无密钥则关掉编码，适配提示词仍可失败降级 |
| `3.3` | 熔炉桌面 | 托盘 / 随叫随到的「熔炉」；仍是同一个 Grok Agent，里面仍然没有工具 |

`3.0` 不依赖 Grok。`3.3` 不依赖把所有闸门都配成熔炉。

## 4. Phase 1：3.0 可配置的熔炉

### 4.1 产品

- [ ] 设置或成员库出现「熔炉」（用户理解为 Grok Agent，不是工具箱）。  
- [ ] 新建成员：可选「请熔炉适配」（改代码路径，可跳过）。  
- [ ] 新建/编辑流程步骤：可选「增加适配节点」（可跳过）。  
- [ ] 新建群模板：可选请熔炉协助（可跳过）。  
- [ ] 闸门 / 人工步骤：执行者可配 **人** 或 **熔炉**。  
- [ ] 熔炉处理闸门时，对话里仍有闸门卡与结果，和人处理同一套时序。

### 4.2 暂不做

- 不接 Grok（入口可先占位）。  
- 不做熔炉桌面形态。  
- 不在熔炉内做工具列表。  
- 不让熔炉默认批准所有闸门。

### 4.3 验收

- [ ] 不选熔炉时，加成员 / 建群 / 闸门与 2.x 行为一致。  
- [ ] 关掉熔炉成员后，已存在的群和脚本成员仍能跑。  
- [ ] 配成熔炉的闸门不会绕过节点状态机。

---

## 5. Phase 2：3.1 两条适配路径

- [ ] **加人路径**：适配提示词 → Grok 改代码（包装 / JSONL / 成员配置草案）→ 闸门确认 → 写入与手建成员相同的表。  
- [ ] **加节点路径**：适配提示词 → 在流程中插入 **适配节点** → 闸门确认 → 与普通节点同一套状态机。  
- [ ] 两套提示词分册，可独立升级。  
- [ ] 适配失败：明确错误，用户可改回手填成员或手建步骤；PTY 仍可当 L0 终端用。  
- [ ] 熔炉内不得出现「已安装工具」列表。

验收：示例 CLI 经「加人改代码」成为带 JSONL 的成员；另一次经「加适配节点」接到流程，提问能进闸门。

---

## 6. Phase 3：3.2 Grok Build 式编码

- [ ] 设置中配置提供方与密钥（本机，不进 JSONL / 群报告）。  
- [ ] 熔炉「写代码 / 构建」任务启动 PTY 中的约定执行体，不直连一套无进程治理的沙箱。  
- [ ] 无密钥或提供方不可用：编码能力关闭，加人适配仍可用。  
- [ ] 厂商协议变化时只换提供方模块，不改会话/节点模型。

验收：一次「改文件 + 跑构建」在工作台终端可见、可停止、可进节点结果。

开放：Grok Build 具体 API / 产品名以当时官方为准；本文只锁「可替换的编码构建提供方」。

---

## 7. Phase 4：3.3 熔炉桌面

- [ ] 独立小窗或托盘入口，产品名「熔炉」，随叫随到。  
- [ ] 可切换回完整工作台（三栏 + 内嵌 TUI）。  
- [ ] 熔炉桌面内加人 / 建群 / 过闸门走同一 API。  
- [ ] 不维护第二份 SQLite。  
- [ ] 通知（构建完、闸门等人）后置可做，但不得替代闸门 UI。

验收：只开熔炉桌面能完成「加人改代码适配」或「加适配节点」之一；切回工作台能看到同一群、同一终端。熔炉桌面里仍然没有工具箱。

---

## 8. 测试与安全（随 3.0 起）

- 熔炉闸门与人闸门同一套 `waiting_human` / 完成语义（或显式新状态，但不可无记录推进）。  
- 熔炉不能提交任意 shell 绕过成员白名单（沿用 2.x：只跑批准的执行体）。  
- 云端请求不把本机 Token、Adapter 原文、完整密钥写入聊天默认可见字段。  
- 熔炉桌面与浏览器工作台同一 Origin / 本机令牌模型。

---

## 9. 2.x 仍后置、不因 3.x 提前吞掉的

专用 Claude/Codex Adapter、服务重启接管 PTY、L3 工作流协同、条件分支并行。熔炉 3.1 用包装脚本 + JSONL 覆盖「多数 CLI」，不替代专用解析器需求时的另案。

---

## 10. 3.x 完成定义（封板口径，未到日期）

同时满足才可称 3.x 主题落地：

- 加人、加节点、建群可选熔炉；闸门可配熔炉；默认仍可全程不用熔炉。  
- 熔炉无内置工具；两条适配路径的产出可脱离熔炉运行。  
- 工作台 TUI 与熔炉桌面可切换且共用数据（若 3.3 已做；若只做到 3.1/3.2，封板说明须写清桌面形态未做）。  
- 编码能力可关；JSONL 契约未被替换。  
- 文档：本文、README 路线图、脚本指南中的「熔炉产出成员」说明齐备。
