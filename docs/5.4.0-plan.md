# 5.4.0 计划：完整的系统通知（桌面端优先）

> 目标：用户把工作台放到后台、最小化到托盘、或在别的应用里干活时，**需要人介入的事一定能被及时、准确、不烦人地通知到**，点击通知能直达对应位置。
> 定位：5.3.0 把"可追溯"做出来后，5.4.0 让 oh-my-co-work 真正成为"可以放着不管、有事才叫我"的桌面协同台——这是"人是活的"理念在桌面端的落点。
> 约束：纯本机；不引入推送服务、不上传任何内容；通知正文遵守现有脱敏规则。
> 标注：**P0** 本版核心；**P1** 重要；**P2** 有空再做。状态 `[ ]` / `[x]` 维护。原 5.3.0 的 DSK-02 并入本文。

---

## 一、现状（读代码确认）

- Electron 主进程有 IPC `acw:notify`（`electron/main.js`），只做 `new Notification({ title, body }).show()`，**没有点击回调、没有图标、没有声音/静音控制、没有去重、没有开关**；
- 渲染端 `useDesktopBridge.js` 有 `notify()` 封装（无桌面桥时回退 Web `Notification`）；**5.2.0 起** `gate.request` 在窗口失焦/隐藏时会经 IPC 发系统通知（含去重 id 与会话 deepLink），其余事件仍待映射（NTF-02）；
- 启动时仅有一处通知（托盘可用时的提示），其余无；
- 托盘只有「打开工作台 / 隐藏到托盘 / 退出」，**无未读/待办角标**，窗口隐藏后用户完全感知不到会话状态；
- 服务端事件总线已有可用的事件：`gate.request`（需人确认）、`node.status`、`session.status`、`session.archived`、`session.interrupted`、`announcement.updated`、`terminal.exited`、`terminal.adapter_error` 等，但没有"通知语义层"把它们归类；
- 设置页没有任何通知相关选项；`preload.cjs`（5.1.0 已修沙箱兼容）可以安全扩展受限 API。

结论：**通道（IPC）有了，但"何时通知、通知什么、点了去哪、怎么关"整套产品逻辑是空白。**

## 二、产品设计

### 2.1 通知分级

| 级别 | 含义 | 默认行为 |
| --- | --- | --- |
| **需要你**（action） | 不处理流程就停着：人工闸门待确认、等待人工输入、CLI 要求登录/授权、终端等待选项 | 窗口不在前台时必发；带声音；持续提醒（可配置间隔，最多 N 次） |
| **出错了**（error） | 步骤失败、终端异常退出、启动失败、服务重启中断 | 窗口不在前台时必发；可合并 |
| **完成了**（done） | 流程跑完、会话归档、长任务结束、文档/报告已生成 | 窗口不在前台时发；静默（无声音）；同会话合并 |
| **提示**（info） | 更新可用、备份/导入完成、配额接近上限 | 默认只在应用内提示，不发系统通知 |

### 2.2 触发规则（何时不通知）

- **窗口在前台且正在看该会话**：不发系统通知，只做应用内高亮；
- **勿扰**：用户开启系统勿扰/专注模式、或应用内勿扰时段内，仅累计到"错过的通知"，不弹出；
- **去重与合并**：同一会话、同一类事件在 N 秒内合并为一条（"3 个步骤待确认"）；同一事件不重复弹；
- **节流**：全局每分钟最多 M 条，超出折叠为一条汇总；
- **已处理自动撤回**：事件已在应用内处理（如已点通过）则撤销尚未被点击的通知（Windows 工具包通知中心、macOS 通知中心均支持移除）。

### 2.3 点击行为（动作）

- 点击通知：**唤起主窗口 → 路由到对应会话 → 定位到具体节点/闸门/终端/文档**（深链）；窗口隐藏在托盘时先恢复显示；
- 通知上的操作按钮（平台支持时）：
  - 闸门：`通过` / `拒绝`（拒绝需回应用填写原因，通知按钮仅做"通过"需二次确认策略可配置，默认**只做"查看"**以防误触）；
  - 错误：`查看日志` / `重试本步`；
  - 完成：`查看报告`；
- 内联回复（macOS）作为 P2：把一句话回给等待输入的节点。

### 2.4 通知内容规范

- 标题：`[会话名] 事件类型`（例：`[发版检查] 等你确认`）；正文一行说明 + 关键对象（节点名、失败原因摘要，截断到 120 字）；
- 图标使用应用 Logo；级别用图标角标/emoji 前缀区分（不依赖平台特性）；
- 正文统一经过**脱敏**与**路径简化**（不展示完整本地绝对路径、不展示命令里的密钥）；
- 文案集中管理（承接 i18n），可预览。

  新建 `electron/lib/notifier.mjs`：统一入口 `notify({ id, level, sessionId, nodeId, title, body, deepLink, actions })`，负责去重/合并/节流/勿扰/前台判断/撤回/记录；渲染端与服务端都只调用这一层。
- [x] **NTF-02 P0 [5.2.0 部分 + 完成类已补：session done/archived 与 announcement.updated → level done（服务端意图层，稳定 eventId；前台/勿扰沿用渲染端策略）] 服务端事件 → 通知语义映射**

## 四、技术方案要点

1. **主进程集中管理**：所有系统通知经 `notifier`，渲染端只通过 `preload.cjs` 暴露的受限 API（`notify`、`clearNotifications`、`setBadge`、`onNotificationClick`），入参逐项校验（长度、级别枚举、deepLink 白名单）。
2. **事件来源**：优先让**主窗口渲染进程**订阅 WS 并产生通知意图（已有会话上下文、设置与前台状态）；窗口被销毁/隐藏时 WS 需保持（`backgroundThrottling: false` 或改由主进程直连服务端 SSE/WS 订阅）——**建议 5.4.0 在主进程增加一条轻量订阅**，不依赖渲染进程存活。
3. **幂等与持久化**：通知意图带 `eventId`；本地表 `notifications(id, event_id, level, session_id, node_id, title, body, deep_link, created_at, read_at, delivered_at, cleared_at)`；重启后按 `cleared_at` 过滤，避免重复推送旧事件。
4. **配置存储**：沿用 `appSettings`，新增 `notifications` 段（含迁移默认值）；服务端提供读写接口，主进程启动时拉取并监听变更。
5. **安全与隐私**：正文脱敏、路径简化；不把通知内容写入系统日志；`/api/notify` 需本机令牌、来源与频率限制；关闭"在通知中显示内容"选项时，只显示"有 1 件事需要处理"。
6. **可测试性**：`notifier` 的去重/合并/节流/勿扰/前台判断做成纯函数，注入时钟与平台，**单测覆盖**；Electron 层用假的 `Notification` 做集成测试；真实弹出走实机检查清单。

## 七、风险与取舍

- **平台限制**：Windows 通知按钮需要 Toast XML 与应用注册，Electron 原生 `Notification` 的 `actions` 在各平台支持不一；5.4.0 以"点击直达"为主，按钮为 P2；
- **后台节流**：若依赖渲染进程订阅，窗口隐藏后事件可能延迟——因此建议主进程直连订阅（见 §4.2）；
- **打扰成本**：宁可少发、可合并，也不要刷屏；默认策略偏保守（`完成了` 静默、`提示` 不发系统通知）；
- **隐私**：通知会出现在锁屏/共享屏幕中，提供"隐藏内容"选项并默认对含路径/命令的事件做摘要化。
