## 1. 一句话

**熔炉**是 3.x 的产品名：工作台里可被配到「加成员 / 建群 / 某扇闸门」上的内置成员，桌面上就是随叫随到的同名助手（简易桌面版 Grok Build）。两种形态是同一熔炉，不是两个品牌。**Adapter（JSONL）仍是融合契约，不是熔炉本身。**

工作台（oh-my-co-work）主题不变：Workflow = 群聊，工具 = 成员，关键处可配人闸门，终端仍是执行载体。桌面入口对外就叫熔炉。

---

## 2. 和 2.x 怎么接

| 层 | 是什么 | 谁负责 |
|----|--------|--------|
| PTY / 终端守护者 | 工具在工作台里像真实终端一样活着 | 2.x，继续保留 |
| JSONL Adapter | 子工具往侧通道写事件，进入对话、闸门、节点、群报告 | 2.x 契约，3.x **不改门、只帮工具走进门** |
| 熔炉 | 适配、创造成员、必要时写代码；加人/建群/闸门上可选用 | 3.x |

判定有没有跑偏：

> 关掉熔炉，它造出来的工具还能不能当普通成员跑。能，就是工作台；不能，就是绑死在一个超级 Agent 上。

---

## 3. 熔炉出现在哪（已决方向）

不是常驻中栏、取代群聊的神助手。三处入口，同一套角色：

### 3.1 添加新成员时可用

人手填脚本路径、Adapter、工作目录仍然保留。可选「请熔炉适配」：根据要接的工具生成或改好该成员（命令、cwd、是否打开 JSONL）。产出是普通 `script` / 终端成员，不是熔炉私有对象。

### 3.2 添加新群聊 / 群模板时可用

可选请熔炉拼成员和步骤。产出仍是普通群模板：关掉熔炉后群还能开聊、还能跑。

### 3.3 闸门可配置成熔炉

闸门执行者可配：**人**（默认）或 **熔炉**（或后续其它成员）。需要人盯的步骤继续配人；适配方案审核、补成员配置、要不要把新工具拉进群，可以配熔炉。闸门还是闸门，只是执行者多了一种。

配置形态后细化，本文只锁定「闸门可把执行者设为熔炉」。

## 4. 熔炉能做什么（能力，不是第一期范围）

按与主题的距离：

1. **适配节点工具**：给一个 CLI，写出包装 + 打开 JSONL Adapter，使人在群里能看到提问、工具卡、结果。  
2. **创造节点工具**：生成成员配置（command、`executionMode`、工作目录），入群后与手建成员无区别。  
3. **当 Agent 写代码**：又一次终端执行（走 PTY）；改仓库、跑构建，结果仍进对话卡和节点。对接 **Grok Build** 时，编码/构建能力走这条，不另开一套脱离工作台的 IDE。

第一期建议只做 1，2 紧随；3 依赖模型对接与桌面形态，见计划文档。

---

## 5. 桌面形态：就叫熔炉（简易桌面版 Grok Build）

### 5.1 已决命名

桌面随叫随到的助手 **产品名就是熔炉**，不再使用「桌面精灵」作正式名称。托盘、小窗、热键唤起的都是熔炉；工作台三栏 + 内嵌 TUI 仍叫 oh-my-co-work（终端守护者）。**可切换的是形态，名字不换两套。**

体感接近简易桌面版 [Grok Build](https://grok.com) 式编码助手——能叫来、能改代码、能跑构建——但账本仍是本机群聊工作台。

### 5.2 和主题的关系：不必然偏离，但有条件

**不偏离**，若同时满足：

- 熔炉桌面与工作台共用本机 server、同一会话、同一成员、同一闸门和终端。  
- 熔炉里「做一个工具 / 开一个群」仍落到加成员、建群、可配置闸门。  
- 写代码仍进 PTY 与（若有）JSONL，而不是桌面窗自己藏一份无账本的执行。  
- 用户可切回完整三栏工作台（群聊 + 流程轨 + 终端），熔炉桌面不是唯一入口。

**会偏离**，若变成：

- 只有熔炉小窗聊天，群、成员、闸门都成了后台细节。  
- Grok 云端会话与本机 Workflow 两套账。  
- 熔炉绕过闸门直接改成员或推进节点。  
- TUI 终端降级成调试窗，不再是一等执行载体。

结论：**熔炉 = 可配置成员 + 桌面助手同一品牌；Grok Build 是「写代码」能力的一种模型来源。** 产品中心仍是群聊工作台，熔炉不是独立于 oh-my-co-work 的第二个 App 宇宙。

### 5.3 必须写明的风险

| 风险 | 说明 | 应对方向（后细化） |
|------|------|-------------------|
| 本地优先 vs 云模型 | 2.x 数据在本机；Grok Build 通常要云端 API | 熔炉调用云模型可配；会话、代码、终端日志默认仍落本机；密钥不进 Adapter JSONL |
| 双形态分裂 | 桌面一套操作，工作台另一套 | 同一 REST/WebSocket；桌面只是薄壳 |
| 神 Agent | 所有闸门都配熔炉，人消失 | 默认闸门仍是人；熔炉是可选项 |
| 供应与条款 | Grok / Grok Build 接口、配额、地域会变 | 模型提供方做成可替换；熔炉不写死单一厂商于引擎内核 |
| 桌面壳技术 | 原设计已有 GUI 壳后置 | 与技术设计中的桌面壳合并为「熔炉」桌面形态，避免三个壳 |

## 6. 非目标（3.x 也不做或明确后置）

- 用熔炉替换 JSONL 契约，或解析终端画面充当 Adapter。  
- 多人同时控制同一 PTY（2.x 已非目标）。  
- 条件分支 / 并行画布（1.x 后置，不因熔炉提前做）。  
- 熔炉默认拥有全部闸门批准权。  
- 纯云端托管工作台（与本地优先冲突，除非另开产品线）。

## 7. 名词

| 词 | 含义 |
|----|------|
| Adapter | 融合**契约**：可信 JSONL 侧通道。门。 |
| 熔炉 | **同一品牌的两面**：工作台里可配到加人、建群、闸门的成员；桌面上随叫随到的助手（托盘/小窗）。走进门的工兵。 |
| 终端守护者 / 工作台 | oh-my-co-work 三栏 + 内嵌 TUI；与熔炉桌面可切换。 |
| Grok Build | 3.x 意向中的编码/构建能力来源；对接方式后细化，不锁死实现。 |

## 8. 开放问题（后细化）

- 熔炉是内置 `kind`、特殊成员模板，还是可安装的执行体？  
- 闸门执行者配置：仅「人 | 熔炉」，还是任意成员？  
- Grok 鉴权放本机设置还是环境变量；无密钥时熔炉如何降级（只适配、不写代码）。  
- 熔炉桌面用现有「打开本机 UI」还是独立小窗 + 托盘。  
- 工作台 ↔ 熔炉桌面切换是窗口级还是同一页内形态开关。

## 9. 讨论来源

2026-08-18 产品讨论纪要（已收口进本文，不另开聊天记录）：

- 2.x Adapter 的意义是翻译「终端里发生的事」→「工作台账本」；通用靠 JSONL 契约，不靠为每个 CLI 写解析器。  
- 熔炉适合做 3.x 主题：加人、建群时能用；闸门可配成熔炉。  
- 熔炉可适配、可创造节点工具、可当 Agent 写代码。  
- 桌面形态 **就叫熔炉**（不再用「精灵」作产品名），意向对接 Grok Build；**保留工作台 TUI，可切换**。  
- 约束：熔炉是可配置角色 + 桌面助手同一品牌，不是新的工作台中心。
